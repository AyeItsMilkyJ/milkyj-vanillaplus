# MilkyCraft Vanilla+ Creator Capture

## Current release status

Creator Capture is **not enabled in the public pack**. It is optional by policy and currently unavailable because neither requested Forge 1.20.1 candidate passes the pack's loader gate:

- Recordium `replaymod-1.20.1-1-shadow.jar` fails while Java builds the Forge module layer. Its shaded Jackson classes collide with Jackson classes supplied through MilkyCraft Vanilla+'s Groovy/Jar-in-Jar stack.
- Free Camera `freecamera-1.20.1-forge-2.2.0.jar` declares `javafml [62,)`; MilkyCraft Vanilla+'s Forge 47.4.10 supplies JavaFML 47. The legacy build also manipulates the local player's physics/input while active and does not provide follow shots or camera-path recording.

The candidates are quarantined as metadata in `creator-capture/candidate-registry.json`. No candidate JAR, Packwiz entry, default configuration, keybind or server file is shipped. Do not manually copy either tested JAR into a MilkyCraft Vanilla+ instance: both prevent the full pack from loading.

This is an implemented fail-closed creator layer, not an abandoned proposal. Repository validation now rejects accidental candidate leakage into the normal Packwiz payload or server set. A future compatible candidate can use the existing Packwiz updater once it passes the gates below; no second updater is needed.

## Pack-owner enablement

There is currently no safe switch to turn on. When a compatible Forge 1.20.1 build becomes available, the pack owner must:

1. download it from the authoritative project and record its project/version ID, filename, license, source revision and SHA-512 in the candidate registry;
2. test it in a disposable client copied from a clean Packwiz install, never in a live player instance;
3. pass every applicable gate in the test matrix below;
4. add one standard Packwiz metafile under `packwiz/mods/` with `side = "client"`, `[option] optional = true` and `default = false`;
5. leave replay folders, render output, `config/replaymod.json`, keybinds and all personal video/shader settings unmanaged;
6. regenerate Packwiz metadata, run the complete validators, build the normal Prism bootstrap and test both opt-out and opt-in installs;
7. confirm the server updater still resolves exactly the normal server JAR set and never receives the creator JAR.

The optional choice must be managed by the existing Prism pre-launch Packwiz installer. A second download script, hand-maintained `mods` folder or separate update feed is not permitted.

## Intended recording workflow after eligibility

The following workflow reflects capabilities present in the inspected Recordium artifact, but it is **not available in the current release**.

1. Enable the future optional Creator Capture component through the pack's Packwiz option, then launch the same Prism instance normally.
2. Open Replay settings and confirm multiplayer recording is enabled. Recordium's inspected defaults enable server recording, automatic start and the on-screen recording indicator; pack defaults must not silently override a creator's later choice.
3. Join the server and confirm the recording indicator is visible before relying on the session.
4. Add an event marker when something interesting happens. The inspected build registers `M` by default, but MilkyCraft Vanilla+ already has many controls, so the creator must resolve the binding in Minecraft's Controls screen. The pack must not overwrite `options.txt` or choose a binding on the player's behalf.
5. Disconnect normally and wait for replay post-processing/rename prompts to finish. Do not kill Java while a replay is being finalised.
6. Preserve the newly created `.mcpr` as immutable source media. Make a working copy before opening it for marker edits, timelines or rendering.
7. Open the working copy from the Replay Viewer. Use pause, seek and speed controls to find the event, then move the replay camera independently from the recorded player.
8. Add position and time keyframes, choose interpolation, preview the path, and render only from the working copy.
9. Keep the original replay, working replay, OBS recording and rendered shots together with their unmodified timestamps. Prophet's future read-only boundary is documented in `CREATOR-REPLAY-INTEGRATION.md`.

Recordium's automatic filename is generated by the mod and can be renamed through its post-recording dialog. No naming configuration was found that is safe to impose through Packwiz. A recommended manual name is `YYYY-MM-DD_HH-mm_dimension_short-event.mcpr`; do not put player IP addresses or private server details in filenames.

## Controls and privacy

- No creator keybind is shipped because no candidate is enabled.
- If a future Recordium build is accepted, its default marker key (`M`) and replay/path keys must be reviewed against Xaero, Controlling and existing gameplay bindings on the actual client.
- Recordium metadata can store server name/address and player identifiers already visible to the client. Treat `.mcpr` files as private source media unless the creator has reviewed them.
- Never commit or upload `options.txt`, `servers.dat`, account files, replay caches, private server details or raw recordings by default.
- Live free-camera behaviour must not move the real player, cancel network movement, alter packets or provide a gameplay advantage. The evaluated Free Camera legacy build did not meet the conservative acceptance rule.

## Rendering and FFmpeg

The inspected Recordium code uses an external FFmpeg process for normal encoded video. On Windows it searches for an executable at `.minecraft/ffmpeg/bin/ffmpeg.exe`, in versioned FFmpeg subdirectories beneath `.minecraft`, or by an explicitly configured command. MilkyCraft Vanilla+ does not bundle FFmpeg: its binary distribution and licensing must be reviewed separately.

Because Recordium cannot launch in this pack, no FFmpeg render was attempted and no rendering claim is made. If replay playback becomes stable before direct rendering does, use OBS or another external capture tool while playing the cinematic path and keep this as a documented manual workflow. Do not add screen-coordinate automation.

## Troubleshooting

### Replay fails to open

Work on a copy, verify the file is a completed `.mcpr` rather than a `.tmp`/cache directory, and preserve the original. Recordium has an upstream multiplayer replay playback issue, so a failure is not proof that the recording itself should be deleted.

### Recording was not saved

Check for a completed file in `replay_recordings`, then inspect `replay_recordings/raw`, `replay_recordings/recording` and `.replay_cache` without modifying them. Preserve temporary data and the game log for diagnosis. Do not repeatedly open or rename the only copy.

### Shader or render conflict

Retest the working replay with shaders disabled. Then test only one known-good pack shader, without changing the creator's global shader selection. A successful no-shader replay does not establish compatibility with every shader.

### Distant Horizons artefacts

Retest with DH rendering disabled while leaving the replay untouched. LODs are client-generated visual data, not authoritative replay content. Do not rewrite the source replay to hide visual artefacts.

### Creator mod is disabled

That is the current expected state. `python scripts/validate_creator_capture.py .` explains which candidates are quarantined. Do not bypass the gate by manually installing the tested JARs.

## Re-evaluation evidence to retain

For each future candidate, retain the exact artifact hash, source revision, client JAR count, server JAR count, loader output, main-menu proof, redacted multiplayer results, replay sizes/durations, Create/DH/shader/dimension observations, FFmpeg command/version, rendered-file hash, normal shutdown result and a statement that no live world or instance was used.
